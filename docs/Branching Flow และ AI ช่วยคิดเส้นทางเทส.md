# ไอเดียเสริม: Branching Flow (Multiverse) และ AI ช่วยคิดเส้นทางเทส

เอกสารเสริมของ Test Studio อธิบายการมองเทสเป็น "แผนที่เส้นทาง" ที่แตกแขนงได้ด้วย React Flow และให้ AI ช่วยเสนอเส้นทางเพิ่มจาก Happy Flow

**สถานะ:** ร่างสำหรับคุยกับทีม

---

## 1. แนวคิดหลัก

เทสมักไม่ใช่เส้นตรง แต่เป็น **ทางปกติ 1 ทาง + ทางผิดพลาดหลายทาง** เหมือนเส้นเวลาแบบ multiverse ที่เดินมาถึงจุดหนึ่งแล้วแตกเป็นหลายเส้น

```
                              ┌─► [Validate: ชื่อว่าง] ──► [เช็ค error]
[เปิดหน้าฟอร์ม] ─► [กรอกข้อมูล] ─┼─► [Validate: อีเมลผิดรูปแบบ] ─► [เช็ค error]
                              └─► [Submit สำเร็จ] ─► [เช็คในรายการ] ─► [ลบข้อมูล]
```

- **Node** = เคสหนึ่งชุด (มีหลาย step ข้างใน)
- **Edge** = เส้นเชื่อมลำดับ อาจติดป้าย เช่น "ทางปกติ", "ทางผิดพลาด"
- **เส้นทาง (Path)** = การเดินจาก Start ไปปลายทางหนึ่งเส้น แต่ละ path คือเทสหนึ่งรอบ

**ประโยชน์**

- เห็นภาพรวมเป็นแผนที่ ไม่ใช่รายการยาว อธิบายให้ทีมและผู้บริหารเข้าใจง่าย
- เห็นช่องว่างของเทสได้ทันที (จุดที่ยังไม่มีแขนง)
- ใช้ชิ้นส่วนซ้ำได้ แก้ที่เดียวกระทบทุกเส้นทาง

## 2. ชนิดของ Node

| Node | หน้าที่ | ช่วงที่ทำ |
| --- | --- | --- |
| Start / End | จุดเริ่มและจบ | เดโม |
| Test Case | เคสหนึ่งชุด ดับเบิลคลิกเข้าไปแก้ step | เดโม |
| Block | ชิ้นส่วนใช้ซ้ำ เช่น Login | เดโม (แบบง่าย) |
| Checkpoint | จุดเช็คระหว่างทาง | Phase 2 |
| Branch (เงื่อนไข) | แยกทางตามเงื่อนไข/ชุดข้อมูล | Phase 2 |
| Group | จัดกลุ่ม node เพื่อลดความรก | Phase 2 |

## 3. หลักการทำงานตอนรัน

### 3.1 ปัญหาเรื่อง state ตอนแตกแขนง

เบราว์เซอร์มีหน้าเดียว แยกร่างไปทำหลายทางพร้อมกันไม่ได้ (ต่างจากหนัง) จึงมี 3 วิธีรับมือ:

| วิธี | ทำอย่างไร | ข้อดี | ข้อเสีย |
| --- | --- | --- | --- |
| **A. เล่นซ้ำจากต้น** | แต่ละแขนงเริ่มจาก Start ไปถึงจุดแยกแล้วเลือกทางตัวเอง | ง่ายและเสถียรที่สุด | ช้าลงเล็กน้อย |
| B. เก็บสถานะที่จุดแยก | ใช้ `storageState` (cookie/session) เริ่มแขนงจากสถานะนั้น | เร็วกว่า | ใช้ได้เมื่อสถานะอยู่ที่ login เท่านั้น ไม่รวมตำแหน่งในหน้า |
| C. เตรียมสถานะต่อเคส | แต่ละเคสไป URL ตรงๆ หลังล็อกอินแล้ว | อิสระต่อกัน รันขนานได้ | ต้องออกแบบเคสให้เริ่มจากสถานะที่รู้แน่นอน |

**เสนอ:** ใช้แบบ A ในเดโม

### 3.2 กติกาของกราฟ

- เดโมใช้ได้เฉพาะกราฟแบบไม่วนกลับ (DAG) ห้ามมีลูป
- ถ้าเคสกลางทางพัง แขนงที่ตามหลังเคสนั้นเป็น **ข้าม (skipped)** ส่วนแขนงอื่นที่ไม่เกี่ยวข้องรันต่อ
- เคสเดี่ยวต้องรันแยกได้เสมอ ไม่บังคับต้องรันผ่านกราฟ
- ข้อมูลที่ส่งต่อระหว่าง node (เช่น ID ที่เพิ่งสร้าง) เก็บในตัวแปรของ flow (Phase 2)

### 3.3 การแสดงผลตอนรัน

node เปลี่ยนสีตามสถานะ: เขียว = ผ่าน, แดง = ไม่ผ่าน, เทา = ข้าม, เหลือง = กำลังรัน

## 4. โครงข้อมูล (JSON)

React Flow ใช้ `nodes` และ `edges` อยู่แล้ว เก็บเป็น JSON ได้ตรงๆ

```json
{
  "name": "Create User Flow",
  "nodes": [
    { "id": "n1", "type": "testCase", "data": { "caseId": "open-form" }, "position": { "x": 0, "y": 100 } },
    { "id": "n2", "type": "testCase", "data": { "caseId": "fill-form" }, "position": { "x": 250, "y": 100 } },
    { "id": "n3", "type": "testCase", "data": { "caseId": "validate-empty-name", "status": "draft", "source": "ai" }, "position": { "x": 500, "y": 0 } },
    { "id": "n4", "type": "testCase", "data": { "caseId": "submit-success" }, "position": { "x": 500, "y": 200 } }
  ],
  "edges": [
    { "id": "e1", "source": "n1", "target": "n2" },
    { "id": "e2", "source": "n2", "target": "n3", "data": { "label": "ทางผิดพลาด" } },
    { "id": "e3", "source": "n2", "target": "n4", "data": { "label": "ทางปกติ" } }
  ]
}
```

ฟิลด์ `status: "draft"` และ `source: "ai"` ใช้แยก node ที่ AI เสนอและยังไม่ได้รับรอง

## 5. AI ช่วยคิดเส้นทางเพิ่ม

### 5.1 หลักการ: AI เสนอ คนอนุมัติ

```
Happy flow ที่ tester ทำ
        ↓
ดึงข้อมูลหน้าเว็บจริงของแต่ละ node (ประเภท input, required, maxlength ฯลฯ)
        ↓
ส่งให้ AI วิเคราะห์ → AI เสนอ "แขนงใหม่" เป็น node/edge
        ↓
แสดงเป็น node เส้นประ (draft) บน React Flow
        ↓
Tester ติ๊กรับ / แก้ / ลบ → เป็นเคสจริง → รันได้
```

**AI ไม่ควรสร้างเคสแล้วรันเลย** ต้องผ่านการตรวจของคนก่อนเสมอ

### 5.2 ข้อมูลที่ต้องส่งให้ AI

- โครง flow ปัจจุบัน (nodes, edges, step ในแต่ละเคส)
- ข้อมูล element ของแต่ละหน้าที่ Playwright ดึงได้: ประเภท input (email, number, password), `required`, `maxlength`, `pattern`, `min/max`, ตัวเลือกใน dropdown
- ข้อความ error ที่หน้าเว็บมีอยู่แล้ว (ถ้ามี)
- คำอธิบายเพิ่มจาก tester (ไม่บังคับ) เช่น "ชื่อห้ามเกิน 50 ตัว อีเมลห้ามซ้ำ"
- รายการเคสที่มีอยู่แล้ว เพื่อให้ AI ไม่เสนอซ้ำ

### 5.3 หมวดที่ AI ควรวิเคราะห์

| หมวด | ตัวอย่างเส้นทางที่เสนอ |
| --- | --- |
| Validation ต่อ field | ว่างเปล่า, ยาวเกิน, ตัวอักษรพิเศษ, อีเมลผิดรูปแบบ, ตัวเลขติดลบ, ช่องว่างล้วน |
| Boundary | พอดีค่า min/max, เกินไป 1 |
| Negative flow | รหัสผ่านผิด, ข้อมูลซ้ำ, ยกเลิกกลางทาง |
| ลำดับผิดปกติ | กดย้อนกลับ, รีเฟรชกลางฟอร์ม, กด submit ซ้ำสองครั้ง |
| สิทธิ์ | ผู้ใช้ไม่มีสิทธิ์เข้าหน้านี้ |
| ข้อมูลไทย/อีโมจิ | ชื่อภาษาไทย, สระซ้อน, อีโมจิ, อักขระพิเศษ |

### 5.4 รูปแบบคำตอบของ AI (JSON ตาม schema)

```json
{
  "suggestions": [
    {
      "branchFrom": "n2",
      "title": "ชื่อว่างเปล่า",
      "category": "validation",
      "priority": "high",
      "confidence": "medium",
      "reason": "ช่องชื่อเป็น required แต่ยังไม่มีเคสเช็ค",
      "steps": [
        { "action": "fill", "target": "ชื่อ", "value": "" },
        { "action": "click", "target": "ปุ่มบันทึก" },
        { "action": "assertVisible", "target": "ข้อความ error ช่องชื่อ" }
      ]
    }
  ]
}
```

**จุดสำคัญ:** ให้ AI อ้าง `target` เป็นชื่อ/ป้ายของ element ที่อยู่ในรายการที่เราส่งไป แล้วให้ระบบของเราจับคู่เป็น locator จริงเอง ห้ามให้ AI เขียน selector ลอยๆ เพราะมักผิด

### 5.5 กลไกลดความผิดพลาดของ AI

| ปัญหา | วิธีรับมือ |
| --- | --- |
| AI อ้าง element ที่ไม่มีจริง | โค้ดตรวจ target ว่ามีในหน้า ถ้าไม่มีให้ตัดทิ้งหรือขอให้ทำใหม่ |
| JSON ผิดรูปแบบ | ใช้ structured output / tool use บังคับ schema และตรวจก่อนใช้ |
| ค่าคาดหวังผิด (AI ไม่รู้ว่าเว็บควรแสดงอะไร) | ลองรันจริงครั้งหนึ่ง จับข้อความที่เกิดขึ้นจริงเป็น "ค่าคาดหวังที่เสนอ" แล้วให้ tester ยืนยัน กันการยืนยันบั๊กว่าเป็นพฤติกรรมที่ถูก |
| เสนอเยอะจนกราฟรก | จำกัด 5-10 แขนงต่อครั้ง เรียงตาม priority |
| ไม่รู้ว่าอันไหนเดามาก | ติดป้าย confidence ให้เห็นชัด |

### 5.6 ประสบการณ์ใช้งาน

1. คลิก node (หรือเลือกทั้ง flow) แล้วกด **"✨ ให้ AI เสนอเส้นทางเพิ่ม"**
2. มีช่องพิมพ์โจทย์เพิ่มได้ เช่น "เน้น validation ภาษาไทย" หรือ "เน้นเรื่องสิทธิ์"
3. กราฟแสดง node ใหม่เป็นเส้นประ มี badge หมวดและ priority
4. กดรับทีละอันหรือรับทั้งหมด แล้วรันได้ทันที

### 5.7 การทำงานทางเทคนิค

- Backend เรียก Claude API พร้อม system prompt บทบาท "QA analyst" และกำหนด schema ผลลัพธ์
- เก็บ API key ฝั่ง server เท่านั้น
- **ความปลอดภัยของข้อมูล:** กรองรหัสผ่าน token และข้อมูลจริงของลูกค้าออกก่อนส่งให้ AI เสมอ

## 6. ขอบเขตที่เสนอสำหรับเดโม

**ทำ**

- Flow Editor ด้วย React Flow (`@xyflow/react`) ลากเชื่อม node ได้
- Node ชนิด Test Case (และ Block แบบง่าย)
- เส้นตรงและแตกแขนงจาก node เดียว
- รันแบบเล่นซ้ำจากต้น (วิธี A) พร้อม node เปลี่ยนสีตามสถานะ
- ปุ่ม AI เสนอเส้นทาง เฉพาะ **Validation ต่อ field** (แม่นที่สุด เห็นผลชัด)
- แสดงผลเป็น draft ให้กดรับ

**ยังไม่ทำ (Phase 2+)**

- Branch เงื่อนไขซับซ้อน, ลูป, ส่งข้อมูลข้าม node
- AI เสนอเรื่องสิทธิ์/ลำดับผิดปกติ และการจับค่าคาดหวังอัตโนมัติ
- Auto layout ขั้นสูง, group node, รันขนาน

## 7. ความเสี่ยง

| ความเสี่ยง | ผลกระทบ | แนวทางรับมือ |
| --- | --- | --- |
| กราฟใหญ่แล้วอ่านยาก | ใช้งานไม่สะดวก | auto layout (dagre/elkjs), จัดกลุ่ม, ย่อ/ขยาย |
| แขนงเยอะทำให้รันนาน | ผลช้า | จำกัดจำนวนแขนง, ใช้วิธี B/C ภายหลัง |
| AI เสนอเคสไม่ตรงกฎธุรกิจ | เทสผิด | ให้คนอนุมัติ, ให้ใส่กฎเพิ่มก่อนวิเคราะห์ |
| ผู้ใช้เชื่อ AI มากเกินไป | พลาดเคสสำคัญ | ติดป้าย draft/confidence, ชี้ช่องว่างที่ AI ไม่ได้ครอบคลุม |
| ข้อมูลลับหลุดไปกับ prompt | ความปลอดภัย | กรองก่อนส่ง, ไม่ใช้ข้อมูลจริง |

## 8. คำถามให้ทีมตัดสินใจ

1. ยอมรับวิธีรันแบบ "เล่นซ้ำจากต้น" ในเดโมหรือไม่?
2. เทสของเราส่วนใหญ่เป็นแบบฟอร์ม/validation หรือมีเส้นทางธุรกิจซับซ้อนมาก (กระทบว่าต้องมี Branch เงื่อนไขเร็วแค่ไหน)?
3. ยอมส่งข้อมูลโครงหน้าเว็บให้ AI ภายนอกได้หรือไม่? (นโยบายข้อมูลของบริษัท)
4. ใครเป็นคนอนุมัติเคสที่ AI เสนอ และมีเกณฑ์ตรวจอย่างไร?
5. อยากวัดผลของฟีเจอร์ AI อย่างไร เช่น จำนวน edge case ที่ AI เสนอได้ตรงเทียบกับที่ tester คิดเอง

## 9. ขั้นตอนถัดไป

1. ทำต้นแบบ Flow Editor ด้วย React Flow ให้ลาก node เชื่อมกันและรันตามกราฟได้
2. ทำ PoC ฟีเจอร์ AI: ดึง field ของ 1 หน้าฟอร์ม ส่งให้ AI แล้วแสดงเป็น draft node
3. ทดลองกับฟอร์มจริงของทีม 2-3 ฟอร์ม แล้ววัดว่า AI เสนอเคสที่ใช้ได้กี่เปอร์เซ็นต์
