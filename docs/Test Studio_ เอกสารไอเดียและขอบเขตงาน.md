# เอกสารไอเดียและขอบเขตงาน: Test Studio (ชื่อชั่วคราว)

เครื่องมือ Web App สำหรับ Tester เขียนและรันเทสเว็บผ่าน GUI โดยใช้ Playwright เป็น engine ไม่ต้องเปิด VS Code หรือรันคำสั่งเอง

**สถานะ:** ร่างสำหรับคุยกับทีม | **เป้าหมาย:** เดโมเวอร์ชันแรก (MVP Demo)

---

## 1. ปัญหาที่อยากแก้

- Tester ที่ไม่ถนัดโค้ดเขียน automation test ไม่ได้ ต้องพึ่ง dev
- การตั้งค่า Playwright (ติดตั้ง, รันคำสั่ง, อ่าน report) เป็นอุปสรรคสำหรับคนที่ไม่คุ้นเครื่องมือ dev
- เทสพังบ่อยเมื่อหน้าเว็บเปลี่ยน และหา locator ที่ดีเองยาก
- ผลเทสอยู่กระจัดกระจาย ส่งต่อให้คนที่ไม่ใช่ tester อ่านยาก

## 2. วิสัยทัศน์และเป้าหมาย

**วิสัยทัศน์:** ให้ tester เปิดเว็บ คลิกเลือก element สร้าง step รันและดูผลได้ในที่เดียว

**เป้าหมายของเดโม:**

1. พิสูจน์ว่าทำ Record → แก้ไข → Run → ดูผลได้จริงบนเว็บ
2. ให้ทีมเห็นภาพและให้ feedback ก่อนลงทุนต่อ
3. ใช้งานภายในทีมได้จริงกับเว็บทดสอบ 1-2 เว็บ

**ตัวชี้วัดความสำเร็จของเดโม**

- สร้างเทส login ง่ายๆ 1 เคส ได้ภายใน 5 นาทีโดยไม่เขียนโค้ด
- รันซ้ำแล้วได้ผลเหมือนเดิม (ไม่ flaky) บนเว็บทดสอบ
- Export เป็นโค้ด Playwright แล้วรันนอกระบบได้

## 3. ผู้ใช้เป้าหมาย

| กลุ่ม | ลักษณะ | สิ่งที่ต้องการ |
| --- | --- | --- |
| Manual Tester (หลัก) | ไม่เขียนโค้ด | บันทึกแล้วรันซ้ำได้ ดูผลเข้าใจง่าย |
| QA ที่เขียนโค้ดได้บ้าง | รู้ Playwright เบื้องต้น | Export โค้ดไปต่อยอดได้ |
| Dev / PM (รอง) | ดูผลอย่างเดียว | รายงานสรุปอ่านง่าย |

## 4. ขอบเขตงานเดโม (MVP Scope)

### ทำในเดโม (In Scope)

| # | ฟีเจอร์ | รายละเอียด |
| --- | --- | --- |
| 1 | จัดการโปรเจกต์/เทสเคส | สร้าง ตั้งชื่อ ลบ เก็บรายการเทสเคส |
| 2 | Browser View | แสดงหน้าเว็บที่ Playwright เปิดอยู่ในหน้าจอเรา ใส่ URL แล้วโหลดได้ |

| 4 | Element Picker | hover เพื่อ highlight คลิกเพื่อเลือก ระบบแนะนำ locator ที่ดีที่สุด |
| 5 | Step Editor | แสดงเป็นรายการ แก้ไขค่า ลบ ลากสลับลำดับ เพิ่ม step เองได้ |
| 6 | Assertion พื้นฐาน | เช็คข้อความ, มองเห็น element, URL, จำนวน element |
| 7 | Runner | กดรัน ดูสถานะแต่ละ step แบบ real-time (ผ่าน/ไม่ผ่าน) |
| 8 | ผลการรัน | screenshot ตอนพัง, log, เวลาที่ใช้, ประวัติการรันย้อนหลัง |
| 9 | Export โค้ด | ส่งออกเป็น Playwright (TypeScript หรือ Python อย่างใดอย่างหนึ่งก่อน) |

### ยังไม่ทำในเดโม (Out of Scope)

- ระบบผู้ใช้หลายคน/สิทธิ์ (เดโมใช้ผู้ใช้เดียวหรือไม่ต้อง login)
- Self-healing locator, Visual diff, AI สร้างเทสจากภาษาธรรมชาติ
- Schedule/CI integration, แจ้งเตือน LINE/Slack
- Cross-browser (เดโมใช้ Chromium อย่างเดียว) และ mobile viewport
- API testing, Data-driven (CSV)
- เว็บที่มี CAPTCHA, iframe ซ้อนซับซ้อน, หลายแท็บ/popup

## 5. Flow การใช้งานหลัก

```
สร้างเทสเคส → ใส่ URL → กด Record → ใช้งานเว็บตามปกติ
→ step ถูกบันทึก → เพิ่ม Assertion → กด Run → ดูผล → Export (ถ้าต้องการ)
```

## 6. สถาปัตยกรรมที่เสนอ

```
[ Frontend: React ]  ⇄ WebSocket/REST ⇄  [ Backend: Node.js ]
                                              │
                                  ┌───────────┴───────────┐
                                  │ Playwright (Chromium) │
                                  └───────────┬───────────┘
                                              │
                                  [ DB: SQLite/PostgreSQL ]
```

| ส่วน | เทคโนโลยีที่เสนอ | เหตุผล |
| --- | --- | --- |
| Frontend | React + TypeScript + Tailwind | ทำ UI เร็ว มี component พร้อม |
| Backend | Node.js (Express/Fastify) | Playwright รัน native บน Node |
| Realtime | WebSocket | ส่ง screencast และสถานะ step |
| Storage | SQLite (เดโม) → PostgreSQL (ต่อยอด) | เริ่มง่าย ไม่ต้องตั้ง server |
| Engine | Playwright | แปลง step JSON เป็นคำสั่งตอนรัน |

### จุดเทคนิคสำคัญ: จะแสดงหน้าเว็บใน Web App ได้อย่างไร

เว็บส่วนใหญ่ฝังใน iframe ไม่ได้ (X-Frame-Options) และ Web App บนเบราว์เซอร์ควบคุมแท็บอื่นไม่ได้ จึงต้องรัน Playwright ฝั่ง server แล้ว:

1. **Screencast:** ใช้ CDP (`Page.startScreencast`) ส่งภาพหน้าเว็บมาแสดงบน canvas ผ่าน WebSocket
2. **ส่ง input กลับ:** ตำแหน่งคลิก/คีย์บอร์ดที่ผู้ใช้ทำบน canvas ส่งกลับไปให้ Playwright ทำซ้ำบนหน้าจริง
3. **จับ element:** ฉีด script เข้าหน้าเว็บเพื่อฟัง event และหา element ใต้เมาส์ แล้วคำนวณ locator ส่งกลับมา

ทางเลือก: เบราว์เซอร์ใน container + noVNC (ทำง่ายกว่าแต่หน่วงและควบคุมละเอียดน้อยกว่า) และ Chrome Extension (ได้ประสบการณ์ดีที่สุดแต่ไม่ใช่ Web App ล้วน) ควรให้ทีมตัดสินใจ

## 7. โครงสร้างข้อมูลเทส (JSON)

เก็บเทสเป็น JSON ที่อ่านได้และ version control ได้ ตัวอย่าง:

```json
{
  "name": "Login Test",
  "baseUrl": "https://example.com",
  "steps": [
    { "id": 1, "action": "goto", "value": "/login" },
    { "id": 2, "action": "fill", "locator": { "type": "label", "value": "Email" }, "value": "admin@test.com" },
    { "id": 3, "action": "click", "locator": { "type": "role", "role": "button", "name": "Login" } },
    { "id": 4, "action": "assertText", "locator": { "type": "css", "value": ".welcome" }, "expected": "Welcome" }
  ]
}
```

**ลำดับความสำคัญของ locator:** role > label > placeholder > test-id > text > CSS id > CSS อื่นๆ (XPath เป็นทางสุดท้าย)

## 9. ความเสี่ยงและข้อควรระวัง

| ความเสี่ยง | ผลกระทบ | แนวทางรับมือ |
| --- | --- | --- |
| Screencast หน่วง/ภาพไม่คม | ใช้งานไม่ลื่น | จำกัดความละเอียด, ปรับ frame rate, ทดสอบเครือข่ายจริงตั้งแต่สัปดาห์ 1 |
| Recorder จับ locator ไม่เสถียร | เทสพังบ่อย | ใช้ลำดับ locator ที่แนะนำ, ให้ผู้ใช้เลือกแก้เองได้ |
| เว็บที่ซับซ้อน (iframe, shadow DOM, popup) | บันทึกไม่ครบ | จำกัดขอบเขตเดโม, ระบุข้อจำกัดชัดเจน |
| ความปลอดภัย: ผู้ใช้ให้ server เปิด URL ใดก็ได้ | SSRF เข้าถึงเครือข่ายภายใน | รันใน container แยก, บล็อก IP ภายใน, จำกัด allowlist |
| เก็บรหัสผ่านในเทส | ข้อมูลรั่ว | แยกตัวแปรลับ (secret) ไม่เก็บเป็น plain text ใน step |
| ใช้ทรัพยากร server มาก (เบราว์เซอร์ต่อ session) | ช้า/ล่มเมื่อผู้ใช้เยอะ | เดโมจำกัดจำนวน session พร้อมกัน |
| ข้อกำหนดการใช้งานของเว็บเป้าหมาย | ปัญหากฎหมาย | ใช้กับเว็บของตัวเอง/เว็บที่ได้รับอนุญาตเท่านั้น |
