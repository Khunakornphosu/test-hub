# Test Studio PoC

ต้นแบบ flow หลักของ Test Studio: แสดงหน้าเว็บที่ Playwright เปิดอยู่ฝั่ง server บน Web App → Record → แก้ไข step → เพิ่ม Assertion → Run → ดูผล/ประวัติ → Export เป็นโค้ด Playwright

## วิธีรัน

```bash
npm install
npx playwright install chromium   # ครั้งแรกเท่านั้น
npm start
```

เปิด http://localhost:3000 ระบบจะโหลดหน้าทดสอบ `/demo-login.html` ให้อัตโนมัติ ส่วนข้อมูลเก็บที่ `data/test-studio.db` (เปลี่ยนที่เก็บได้ด้วย `DB_PATH`)

> ต้องใช้ Node 22.13 ขึ้นไป เพราะใช้ `node:sqlite` ที่มากับ Node ตอนรันจะเห็น ExperimentalWarning ซึ่งไม่มีผลต่อการทำงาน

## ลองใช้งาน

1. กด **● Record** แล้วใช้หน้าเว็บตามปกติ: กรอกอีเมล รหัสผ่าน เลือกบทบาท ติ๊ก "จดจำฉัน" แล้วกดเข้าสู่ระบบ
2. กด **ตรวจข้อความ** แล้วคลิกข้อความต้อนรับ
3. กด **■ Stop** แล้วกด **▶ Run**
4. คลิกที่ step เพื่อแก้ไข, ลาก ⋮⋮ เพื่อสลับลำดับ, หรือกด **+ เพิ่ม Step** เพื่อสร้างเอง
5. ดูผลย้อนหลังที่แท็บ **ประวัติการรัน** ส่วนการรันที่พังจะมี screenshot
6. กด **Export** เพื่อดูโค้ด Playwright (TypeScript) หรือ JSON

## ความปลอดภัย

| ภัย | การป้องกัน |
| --- | --- |
| **SSRF:** ใช้ server เราเปิด URL ภายในองค์กร | ทุก request ของเบราว์เซอร์ทดสอบ (รวม redirect ทุก hop, รูป, fetch, WebSocket) ต้องผ่าน proxy ใน `security.js` ซึ่งกันที่อยู่ภายใน, localhost, cloud metadata และ scheme อื่นนอกจาก http/https ส่วน proxy เชื่อมต่อไปที่ IP ที่ตรวจแล้วเอง (กัน DNS rebinding) และหน้า `/api` ของระบบเองก็เปิดจากเบราว์เซอร์ทดสอบไม่ได้ |
| **คนในเครือข่ายเข้ามาใช้** | ค่าเริ่มต้นฟังเฉพาะ `127.0.0.1` ถ้าตั้ง `HOST=0.0.0.0` โดยไม่ตั้ง `APP_PASSWORD` server จะไม่ยอมเริ่ม |
| **เว็บอื่นแอบสั่งงานผ่าน WebSocket** (CSWSH) / DNS rebinding | ตรวจ `Origin` และ `Host` header ทุก request |
| **ล็อกอิน** | รหัสผ่านเดียว (`APP_PASSWORD`), cookie แบบ `HttpOnly` + `SameSite=Strict`, จำกัดการลองผิด 10 ครั้งต่อ 15 นาที |
| **ตัวแปรลับรั่วจากฐานข้อมูล** | เข้ารหัส AES-256-GCM (`SECRET_KEY` หรือ `data/secret.key`) ค่าเดิมที่เป็นข้อความธรรมดาถูกแปลงอัตโนมัติตอนเริ่มระบบ |

ค่าตั้งทั้งหมดดูได้ใน `.env.example` ส่วนเว็บภายในองค์กรที่ต้องการทดสอบ ให้ระบุใน `ALLOWED_HOSTS`

**ข้อจำกัดที่ยังมี:**
- ผู้ใช้ทุกคนใช้รหัสผ่านเดียวกัน ยังไม่มีบัญชีรายคนและสิทธิ์ (อยู่ใน Phase 3)
- เบราว์เซอร์ทดสอบรันใน process เดียวกับ server ถ้าใช้จริงกับหลายคน ควรแยกเป็น container

## Deploy บน Vercel (ทดลอง)

ใช้ `Dockerfile.vercel` (Vercel Functions แบบ container + WebSocket ซึ่งทั้งสองอย่างยังเป็น beta)

```bash
npx vercel link --project test-studio     # ครั้งแรก
npx vercel env add APP_PASSWORD production # ตั้งค่าที่จำเป็น (ดูรายการด้านล่าง)
npx vercel deploy --prod
```

**Environment variables ที่ต้องมี:**
- `APP_PASSWORD`: จำเป็น เพราะเว็บเปิดบนอินเทอร์เน็ต
- `SECRET_KEY`: ใช้เข้ารหัสตัวแปรลับ
- `PUBLIC_HOSTS=*.vercel.app`
- `GEMINI_API_KEY` และ `GEMINI_MODEL`: ถ้าต้องการใช้ AI

`.vercelignore` กันไม่ให้ `.env*`, `data/` และ `secret.key` ถูกอัปโหลด

**ข้อจำกัดของรอบทดลอง (ต้องแก้ก่อนใช้จริง):**
- **ข้อมูลไม่ถาวรและไม่ตรงกันระหว่าง instance:** ฐานข้อมูลอยู่ใน `/tmp` ของแต่ละ instance จึงหายเมื่อ instance ถูกปิด (ไม่มีคนใช้ 5 นาที) และถ้า Vercel เปิดหลาย instance ข้อมูลจะไม่ตรงกัน (เห็นได้จริงตอนทดสอบ) → ต้องย้ายไป Postgres
- **การเชื่อมต่อหลุดตามเวลาสูงสุดของ function:** Hobby 5 นาที, Pro สูงสุด 13 นาที หน้าเว็บจะต่อใหม่และเปิดเทสเดิมให้อัตโนมัติ
- **ทดสอบเว็บที่อยู่ในเครือข่ายภายในบริษัทไม่ได้**
- แผน Hobby ใช้ได้เฉพาะงานส่วนตัวที่ไม่ใช่เชิงพาณิชย์


- แต่ละเทสสร้างเทสเคสของตัวเองแล้วเปิดผ่าน `/?test=ID` จึงรันพร้อมกันได้

## Phase 2

### Self-healing locator
- **ตอนบันทึก:** เก็บ locator ที่ยืนยันแล้วได้สูงสุด 5 ตัว (ตัวหลัก + สำรอง 4) และ "ลายนิ้วมือ" ของ element ได้แก่ tag, id, name, type, placeholder, aria-label, test-id และข้อความ
- **ตอนรัน:** ถ้าตัวหลักหาไม่เจอเกิน 1.5 วินาที ระบบจะลองตัวสำรอง และยอมรับเฉพาะตัวที่เจอ element 1 ตัวพอดีและลายนิ้วมือตรงกันอย่างน้อย 50% ถ้าไม่มีตัวไหนผ่าน เทสจะพังตามปกติ
- **ผล:** เทสผ่าน แต่แสดงแบนเนอร์สีเหลือง "ซ่อม locator อัตโนมัติ N จุด" และ**ไม่แก้เทสเอง** ผู้ใช้ต้องกด "ใช้ locator ใหม่" เพื่อยืนยัน ป้องกันกรณีเทสผ่านทั้งที่เว็บพังจริง
- **ไม่ซ่อม:** assertCount (การนับจำนวน) ส่วน assertText ที่ข้อความเปลี่ยนจริงจะพังเพราะลายนิ้วมือไม่ตรง
- **Locator health:** step ที่เคยต้องซ่อมหรือพังใน 20 การรันล่าสุดจะมีป้าย เช่น "ซ่อม 1/3"
- **ทดลองได้:** แก้ step "เปิด" เป็น `/demo-login.html?v2` ซึ่งจะเปลี่ยนชื่อช่องอีเมลและข้อความปุ่ม แล้วกดรัน
- step ที่บันทึกก่อนมีฟีเจอร์นี้ยังไม่มีตัวสำรอง ต้องบันทึกใหม่หรือกด "เลือกใหม่จากหน้าเว็บ"
- โค้ดที่ export ใช้เฉพาะ locator หลัก

### Reusable blocks
- step ประเภท **"ใช้เทสอื่นซ้ำ (block)"** จะรันทุก step ของเทสที่เลือก ณ ตำแหน่งนั้น เช่น ใช้เทส Login ซ้ำในทุกเทส
- ใช้ block ซ้อนกันได้ลึก 5 ชั้น ถ้าวนกันเอง (A → B → A) ระบบจะแจ้ง error ตอนรัน
- ถ้า step ใน block พัง error จะบอกว่าพังที่ step ไหนใน block ไหน
- ถ้า step ใน block ถูกซ่อมอัตโนมัติ การกดยืนยันจะไปแก้ที่เทสต้นทาง
- ตอน export จะขยาย block เป็น `await test.step('ชื่อเทส', async () => { ... })` ซึ่งเห็นเป็นกลุ่มใน Playwright report

### AI สร้าง step จากภาษาคน (Google Gemini)

**ตั้งค่า:**
1. ขอ API key ฟรีที่ https://aistudio.google.com/apikey (ล็อกอินด้วยบัญชี Google)
2. `cp .env.example .env` แล้วใส่ `GEMINI_API_KEY=...` ในไฟล์ `.env` (ไฟล์นี้อยู่ใน `.gitignore`)
3. รีสตาร์ท server

ไม่ต้องระบุรุ่นโมเดล ระบบจะดึงรายชื่อรุ่นที่บัญชีใช้ได้ แล้วลองตามลำดับ **flash ใหม่สุด → flash-lite ใหม่สุด → flash รุ่นถัดไป** แต่ละรุ่นลองซ้ำ 1 ครั้ง และตัดที่ 30 วินาที
- จากการทดสอบจริง รุ่นใหม่สุดตอบ 503 "high demand" เป็นช่วงๆ และบางครั้งใช้เวลาเกือบ 60 วินาทีกว่าจะตอบ จึงสลับไปตระกูล lite ซึ่งมักว่างกว่า
- ระบุรุ่นเองได้ด้วย `GEMINI_MODEL` (ระบบจะไม่สลับรุ่นให้)
- ดูโควตาของบัญชีได้ใน AI Studio

**การทำงาน:**
1. เปิดหน้าเว็บที่ต้องการ กดปุ่ม **✨ AI** แล้วพิมพ์สิ่งที่ต้องการให้เทสทำ
2. ระบบส่งคำสั่ง + ARIA snapshot ของหน้าที่เปิดอยู่ + รายการ step เดิม ไปให้ Gemini ซึ่งตอบกลับเป็น JSON ตาม schema ที่กำหนด
3. ทุก step ต้องมีค่าที่ action นั้นจำเป็นครบ (เช่น ข้อความที่จะพิมพ์ หรือข้อความที่ต้องตรวจ) เพราะจากการทดสอบจริง โมเดลบางครั้งใส่ค่าผิดช่อง จากนั้นผ่าน `sanitizeStep` และถูกตรวจกับหน้าเว็บจริง โดยแสดงผลเป็น: พบ element / ยังไม่พบ (อาจอยู่หน้าถัดไป) / เจอหลายตัว / ใช้ไม่ได้ ส่วน step ที่เจอ element จะได้ locator สำรองสำหรับ self-healing ด้วย
4. ผู้ใช้ติ๊กเลือก step ที่ต้องการ แล้วกดเพิ่มต่อท้ายเทส

**ความเป็นส่วนตัว:**
- ค่าที่พิมพ์ไว้ในช่องกรอกทุกช่อง **รวมรหัสผ่าน** จะถูกตัดออกจาก snapshot ก่อนส่ง เพราะ ARIA snapshot ของ Playwright แสดงค่าเหล่านี้เป็นข้อความธรรมดา
- ส่วนอื่นของหน้า (ข้อความ ชื่อปุ่ม) ยังถูกส่งไป Google: ข้อมูลใน free tier อาจถูกใช้ปรับปรุงบริการของ Google จึงไม่ควรใช้กับหน้าที่มีข้อมูลลับ
- เนื้อหาหน้าเว็บถือเป็นข้อมูลที่ไม่น่าเชื่อถือ prompt จึงสั่งให้โมเดลไม่ทำตามคำสั่งที่อยู่ในหน้าเว็บ และผลลัพธ์ต้องผ่าน schema + การตรวจ + การเลือกโดยผู้ใช้เสมอ

## Design system

ใช้ **GitHub Primer** (MIT license) ติดตั้งผ่าน npm ไม่ได้ดึง CSS จากเว็บอื่น
- `@primer/css`: ปุ่ม ฟอร์ม เมนู (SelectMenu), Toast, Counter
- `@primer/primitives`: token สี ขนาด ฟอนต์ และมุมโค้ง รองรับ light/dark อัตโนมัติตามเครื่อง
- `@primer/octicons`: ไอคอน (server สร้าง `/icons.js` ให้ตอนเริ่ม)

Primer CSS v22 ไม่มีคอมโพเนนต์อย่าง Box, UnderlineNav, Flash, Blankslate แล้ว (ย้ายไป Primer React) จึงเขียนเองใน `index.html` ตามสเปก Primer โดยใช้ token ชุดเดียวกัน ถ้าย้ายไป React ภายหลังให้ใช้ `@primer/react` แทนส่วนนี้ได้เลย

หลักการด้าน UX:
- **ปุ่มหลักมีแค่ 2 ปุ่ม:** "บันทึก" และ "รันเทส" ส่วนการตรวจสอบรวมอยู่ในเมนู "ตรวจสอบ" และ Export/ตัวแปรลับอยู่ที่หัวหน้า
- **แบนเนอร์เหนือหน้าเว็บบอกสถานะเสมอ:** พร้อมใช้งาน / กำลังบันทึก / รอคลิก element / กำลังรัน step x จาก y และกด Esc เพื่อยกเลิกโหมดได้
- **step แสดงเป็นภาษาคน:** ไอคอน + คำกริยา + element + ค่า ส่วนโค้ดซ่อนไว้ (ติ๊ก "แสดงโค้ด" เพื่อดู) และ step ใหม่จะกะพริบให้เห็น
- **Step Editor ใช้ "🎯 เลือกจากหน้าเว็บ" เป็นทางหลัก:** ระบบทดสอบ locator ให้อัตโนมัติ ส่วนการแก้ locator เองซ่อนอยู่ใน "ขั้นสูง"

## การเลือก locator

ลำดับ: role > label > placeholder > test-id > text > CSS id > CSS class > CSS path

ระบบตรวจทุกตัวเลือกด้วย Playwright จริง *ก่อน* ส่งคลิกไปหน้าเว็บ ต้องเจอ element 1 ตัวพอดีและเป็นตัวเดียวกับที่ผู้ใช้คลิก ส่วน assertion ข้อความจะเลี่ยง locator ที่อิงข้อความ เพื่อให้ error บอกว่า "ข้อความไม่ตรง" แทน "หา element ไม่เจอ"

- พิมพ์ในช่องรหัสผ่านระหว่าง Record แล้วระบบจะสร้างตัวแปร `TEST_PASSWORD` ของโปรเจกต์ให้อัตโนมัติ step จะเก็บแค่ชื่อตัวแปร
- จัดการได้ที่ปุ่ม **🔒 ตัวแปรลับ** หรือติ๊ก "ค่าลับ" ใน Step Editor ของ step กรอกข้อความ
- หน้าเว็บและ JSON ที่ export ไม่มีค่าจริง ส่วนโค้ดที่ export จะอ่านจาก `process.env.<ชื่อตัวแปร>`

## ข้อจำกัด (ตั้งใจไม่ทำใน PoC)

- ถ้าเปิดเทสเดียวกันหลายแท็บพร้อมกัน แท็บที่บันทึกทีหลังจะทับของอีกแท็บ
- ไม่แสดง popup/แท็บใหม่/iframe ส่วน dialog แบบ `alert()` Playwright จะปิดให้อัตโนมัติ
- Frontend เป็น HTML/JS ล้วนเพื่อให้ทดสอบเร็ว เวอร์ชันจริงค่อยย้ายไป React
